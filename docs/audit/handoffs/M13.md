- Keep all work on refactor/factsport-v2. No production deployment, DNS, routes, secrets, database, scheduler, payment or entitlement changes without separate written approval.

## Schema facts checked

- Migration 0001 creates the clean-start base matches table and the app identity/job foundation. Its base match projection includes canonical/provider IDs, teams, scores, kickoff/status, logos, venue/stage/group, events/stats/lineups/H2H/referees/predictor and provider freshness/version fields.
- Migration 0006 adds season, featured-match flags, homepage settings, standings and highlights structures. It does not add the legacy displayClock, stream/audio/video URLs, widget_id, affiliate_link, pro_analysis, chat-pin fields or legacy campaign_id to matches.
- Migration 0008 adds only a nullable unique legacy_match_id alias. It does not populate aliases or change canonical matches.id.
- Migration 0003 creates the V2 free-prediction contacts/participants/predictions/consent foundation with campaign_snapshot JSON. It does not by itself reproduce the legacy campaigns table/rules and PredictionBoard query/write contract.
- The V2 listPostgresMatchesWindow projection intentionally returns base match fields and does not include displayClock. The existing match page ticker currently selects displayClock from legacy Supabase. Do not switch that ticker to the base reader until a clock/freshness contract is supplied.
- The V2 branch of GET /api/settings currently returns only the featured-match pointer and null affiliate fields. Do not enable FACTSPORT_HOMEPAGE_BACKEND on the public site until the settings model preserves all approved public settings and the affiliate/private-product policy decision is implemented. The existing legacy fallback remains available.

## Nested match-centre service dependencies verified

- PredictionBoard reads matches.campaign_id, campaigns and user_predictions in the browser, and inserts predictions/updates custom_predictions. It remains legacy-backed until campaigns, eligibility, locking, server authorization and settlement parity are delivered (P5).
- FanZoneChat uses the external chat-api.factsport.com Worker for messages, polling every three seconds during live matches. It also writes match chat-pin fields directly through browser Supabase. Pins need server-side admin authorization; chat needs a deliberate same-origin service/DB migration preserving moderation, abuse limits and live polling (P6).
- MOTMVoteWidget calls its external Worker and uses localStorage as a client-side voted marker. The server must enforce vote uniqueness, candidate validity and voting windows; localStorage is not an authorization boundary (P6).
- FactSportPlayer supports raw media, YouTube, generic iframe and StreamIO media-room paths. FactSportMediaRoom obtains Stream tokens through /api/stream/token, which supports anonymous listeners, authenticated users and admin-generated guest invite tokens. Preserve this distinct StreamIO contract while designing playback grants.
- MatchHeaderClient and MatchMobileHub consume MatchLiveProvider and the external live-api path. Keep the current three-second live experience and edge cache; do not route every viewer poll through PostgreSQL.
