# M11 — Hyperdrive request lifecycle correction and staging re-verification

Date: 2026-11-07
Branch: refactor/factsport-v2
Scope: intermittent PostgreSQL 503 remediation and protected staging recheck. No production cutover.

## Finding

Staging runs intermittently returned 503 on the second or cursor-based match read while the initial /matches server render succeeded. Source inspection found two risky details in the app reader layer:

1. postgres.js client was cached in module scope and reused across Cloudflare Worker requests. Cloudflare documents stale I/O-context failures when database clients are created globally and reused across requests.
2. Match projections used sql.unsafe(MATCH_SELECT). Cloudflare's current Hyperdrive/Postgres.js guidance notes that sql.unsafe() can disable prepared statements for those queries, adding round trips and reducing the intended Hyperdrive prepared-statement caching.

References:
- https://developers.cloudflare.com/hyperdrive/observability/troubleshooting/
- https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/postgres-js/

## Remediation committed

- Replaced the module-scoped singleton with withFactsportPostgres(), which creates a client inside each adapter operation and closes it in finally using sql.end({ timeout: 1 }). Hyperdrive remains responsible for backend connection pooling.
- Kept max: 1 per request-scoped client and fetch_types: false; retained prepare: true.
- Replaced dynamic sql.unsafe(MATCH_SELECT) with explicit static SQL projections in the match reader so prepared statements remain enabled.
- Refactored match, editorial, homepage and competition adapters to use the request-scoped helper.
- Added regression assertions that no adapter uses the old global client or sql.unsafe(), that the client is closed, and that the base matches projection does not select season before migration 0006.
- Updated architecture notes in the roadmap, page matrix, production execution plan and M09 handoff. The earlier one-client-per-isolate design is superseded.

## Match-centre migration boundary discovered

The main /match/[id] page is not yet ready for a PostgreSQL flag. It still depends on:
- Legacy match IDs and campaign_id linkage used by PredictionBoard and historical prediction records.
- Stream/audio/video URLs and the 15-minute pre-kickoff player lock. Current client-side unlock behaviour means stream URLs must not simply be copied into a public DTO; delivery needs server-side authorization/entitlement and a signed short-lived playback grant.
- VIP pro_analysis data and profile is_vip checks currently performed in the browser; both need server authorization before exposing analysis.
- GoalRushTicker's extra match clock projection and site_settings announcement data.
- Match events, stats, lineups, H2H, referees and ESPN live updates.
- MOTM, chat, player ratings, prediction writes and other child-component service contracts.

Do not switch the match detail page to PostgreSQL until canonical legacy-ID aliasing/import strategy, campaign/prediction parity, stream delivery authorization, pro-analysis RBAC and same-origin settings/ticker APIs are implemented and tested. The base match list API is not sufficient proof of match-centre parity.
