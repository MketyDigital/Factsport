# AUTH-AI-001 — ZITADEL self-host costs, alternatives, Assist standalone inference
Date: 2026-10-31. Status: source/research verified, architecture decision pending; no provisioning or prod changes.

## ZITADEL decision facts
- Hosted ZITADEL Cloud Free offers unlimited stored users but **100 daily active users**. Cloud Pro starts at **US$100/mo** with 25,000 DAU included. Source: https://zitadel.com/pricing and https://zitadel.com/pricing/detail
- Self-host Community open-source ZITADEL does not impose the Cloud Free account's 100 DAU limit. Core service ~512 MB RAM / <1 CPU in light test; Docker Compose guide asks for host >=2GiB RAM, requires PostgreSQL 14-18, reverse proxy with HTTP/2/gRPC, managed TLS, persistence, backups, monitoring. Production hashing spikes and large HA requirements materially exceed toy test sizing. Sources https://zitadel.com/docs/self-hosting/deploy/overview , https://zitadel.com/docs/self-hosting/deploy/compose , https://zitadel.com/docs/self-hosting/manage/requirements , https://zitadel.com/docs/self-hosting/manage/production .
- Self-host is software-license-free OSS subject to ZITADEL AGPL-3.0; examine legal/compliance especially if modifying redistributing. https://help.zitadel.com/zitadel-licensing-faqs and https://zitadel.com/blog/apache-to-agpl
- New standalone self-host adds compute+TLS/OS/security patching+PostgreSQL workload, backup/restore and an availability dependency. **Do not co-locate with Factsport production B1ms PostgreSQL before CPU credits, memory, connection and load tests.** B1ms is already a capacity-constrained shared DB target.
- Cheapest/least-maintenance starting alternatives: reuse existing Mkety Auth with already running Zitadel if infrastructure exists, isolated Factsport OIDC client/project; or dedicated managed auth such as **Clerk Hobby** which announced 50,000 monthly retained users free per app (different metric from ZITADEL DAU, per-app pricing/limits apply), with extra reliance on vendor SDK and planned external subject mapping. https://clerk.com/pricing and https://clerk.com/changelog/2026-02-05-new-plans-more-value ; or existing Supabase Auth Free 50k MAU **only as temporary separate authentication service**, contrary to end-state Supabase removal and may pause when inactive; would add split architecture. https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/platform/manage-your-usage/monthly-active-users.mdx
- Recommended sequence: first review real Mkety Auth deployment/tenant isolation and DAU; evaluate Clerk if no shared capacity; self-host ZITADEL only when spare current host or measured usage/availability justifies incremental operations. Do not trigger immediate migration solely at 100 DAU; alert earlier and plan, because cutover requires identity linkage and verified sessions.
- **Operational threshold proposal**: daily unique authenticated subjects across all Factsport OIDC callbacks/session validation; dashboard trends at 60, 80, 90 distinct DAU with alert to owner, plus weekly 7d trend and Cloud-hosted quota monitoring, 20% safety margin. Counting daily site visits or login attempts is not same as provider-billed DAU. Never disable logins on projected DAU threshold; trigger migration decision and tested transition.
- User identities remain Factsport canonical stable user UUIDs; `external_identities(issuer,subject,user_id)` mapping, never email-only auto-link; preserve VIP/subscriptions, predictions and authorization. Mkety Mail can handle verification/recovery with provider integration. Signed-in users may need reauthentication on issuer change even when the frontend/app remains stable.

## Mkety SaaS APIs — separate products
Repository `MketyDigital/mksaas` includes both:
A. **Enterprise AI** on main: `src/app/api/v1/ai/chat/completions/route.ts`, `/api/v1/ai/models`. Bearer key scopes `ai:chat` and `ai:models:read`, enterprise entitlement, required `Idempotency-Key`, optional project header, nonstreaming supported. Commercial reservation, cost envelope, failure reconciliation.
B. **Assist standalone Worker** at `customer-apps/assist/src/index.ts` and `src/runtime.ts`. Inspected specifically on branch `plan/assist-api-approval-routing-20261003` (one of several Assist-specific branches) and compared with main. The branch's Worker dispatches `/v1/*` to `handleApiKeyInference`. `POST /v1/chat/completions` authenticates customer `mka_` token, customer-scope active key with `inference` scope, per-key rate limit, commercial budgets. Two modes:
  - `assistant`: assistant_id-bound assistant context, permissions and model alias.
  - `raw_model`: explicit customer `raw_model_api_settings.enabled` plus customer and key model alias allowlists, model route and rate verification; direct completion with stable Mkety model alias, not tied to configured assistant persona.
- On Assist raw_model path, `Idempotency-Key` is optional in inspected branch; **Factsport should still provide a deterministic key** for each AI job. Nonstreaming response uses OpenAI-like shape `choices[0].message.content`; can return 402 credit policy or 429 capacity, and 503 reconciliation depending on failure state. Do not treat all 5xx as safe to retry or rewrite idempotency key. Source paths: `customer-apps/assist/src/index.ts` line ~140; `customer-apps/assist/src/runtime.ts` around ~2750-2970; `customer-apps/assist/src/api-key-policy.ts`.
- `customer-apps/assist/README.md` documents aliases mkety-fast, mkety-smart, mkety-reasoning, mkety-vision. Availability depends on customer routes, permissions, API key mode and billing; don't claim account permission from source existence.
- **Recommendation** for Factsport editorial generation: choose whichever API is actually enabled, more economical and appropriate for scheduled no-persona generation. Enterprise AI (main) is simplest given current passive adapter; Assist **raw_model** is viable alternative if owner already has enabled customer API and allowlisted model. Avoid assistant mode unless a dedicated Factsport editorial assistant's instructions/knowledge are desired.
- **Adapter gap**: existing `lib/adapters/mkety-ai.ts` currently implements Enterprise API only; next add `MketyAssistRawModelAdapter` conforming to same AiProvider and select via env (AI_PROVIDER=mkety-enterprise|mkety-assist). Preserve Mkety Mail as separate first-party direct provider. Never hardcode host/key in public repo or deploy before tenant readiness verified.

## Clerk Hobby free verified 2026-10-31; ZITADEL on same Azure PostgreSQL (not deployed)
Official current Clerk pricing: https://clerk.com/pricing ; https://clerk.com/changelog/2026-02-05-new-plans-more-value
- Hobby $0, **50,000 Monthly Retained Users per app**, unlimited applications, 3 dashboard seats, fixed 7-day session lifetime, 1-day application logs; email/password, email codes, social auth and user management included. "MRU" means returned >=24 hours after signup in the billing month, not MAU or DAU.
- Production MFA and passkeys require paid tier: https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options. Therefore enforce administrator protections separately or budget for Pro; do not claim free MFA.
- >50k MRU requires Pro, Clerk documents 1-month grace; published Pro $25/mo monthly or $20/mo annual, plus overages. Verify on exact billing account before adoption.
- Clerk backend SDK supports Workers edge auth; use stable internal Factsport UUID and mapping (issuer, subject); keep VIP and permissions in Factsport DB. Clerk supports CSV/password-hash export: https://clerk.com/docs/guides/development/migrating/overview . Provider switch still requires session re-login and careful OAuth linking, so "invisible" identity migration is not fully guaranteed.
- For Factsport: candidate **Clerk Hobby** for low-maintenance user auth initially, assuming free plan restrictions suit admin security. Check vinext app integration with server SDK and real login flows in staging; don't assume Next middleware plugin is vinext compatible.

ZITADEL official docs: https://zitadel.com/docs/self-hosting/manage/database ; https://zitadel.com/docs/self-hosting/manage/requirements ; https://zitadel.com/docs/self-hosting/manage/production .
- Self-host ZITADEL may use **the SAME Azure PostgreSQL Flexible Server**, but **dedicated `zitadel` database, own role, TLS DSN, no shared table schema** with Factsport. ZITADEL app still needs separate, continuously running container/server/reverse proxy; an Azure PG server alone cannot host the executable.
- ZITADEL officially supports PG14-18 and documented external managed DB bootstrap `zitadel init schema` (after provisioning appropriate DB/roles). Redis is optional.
- B1ms = 1vCPU/2GiB RAM is low capacity. ZITADEL DB usage and password hashing may exhaust shared CPU credits/connection/memory pool and cause correlated loss of Factsport and login. Self-host ZITADEL and Factsport DB together ONLY after concurrency tests and backup/restore validation; strongly prefer existing separate Mkety Auth/ZITADEL DB if already provisioned and safely isolated.
- Lowest cost immediate decision: Clerk Hobby or existing tested shared Mkety Auth, not a new ZITADEL VM + shared B1ms by default. DAU-based ZITADEL Cloud alert threshold not applicable to Clerk MRU; if Clerk adopted alert at 30k/40k/45k MRU, confirm monitoring metric and monthly cutoff. No alerts configured.
- Maintain portable OIDC/AuthPort; authentication provider switch always needs robust external subject mapping, account merging protections, privilege controls, migration/export, potential reauthentication.
- Neither Clerk nor ZITADEL configured or deployed; no Azure resources touched.
